$0 を todo に分割し、todo.md を作成せよ。

既存の todo.md がある場合は、記録済みのフェーズを維持したまま新規フェーズとして追記する。

## 分割判断

- まず todo.md が必要か判断する
- 1セッションで実装・単体テスト・修正フィードバック対応まで完了できる見込みなら、todo.md は作成しない
- 分割が必要な場合のみ、依存関係・責務境界・概算コード量を元にフェーズを作る
- フェーズ数は固定しない。1個、2個、3個以上のいずれもあり得る
- 1フェーズの概算コード量が 500 行程度を超える見込みなら分割を検討する
- 行数は目安に留め、依存関係・責務境界・実装順序を分割判断の材料にする
- ドキュメント作成は原則として最後のフェーズに寄せる
- フェーズ数は仕様に応じて必要最小限にする

**着手前に対象ファイルの行数を実測する。** 概算コード量は分割要否の判断材料なので、記憶や見当ではなく実測から出す。

**プランに実装順序が書かれていても、そのステップ数をそのままフェーズ数にしない。** 品質ゲート (mypy / pytest) が中間状態で通る単位でフェーズ境界を引き直す。設定項目の削除や抽象メソッドの追加を単独フェーズに切ると、そのフェーズ完了時点で型チェックとテストが通らなくなる。

## フェーズ粒度

フェーズは、別のAIコンテキストでそのまま実装依頼できる単位にする。

- 1フェーズは、仕様確認・実装・対応する単体テスト・フィードバック修正まで一続きで完了できる範囲にする
- 小さな責務差だけではフェーズを分けない
- 同じフィードバックループで修正できる作業は、同一フェーズにまとめる

## ToDo項目の書き方

ToDoは原則として編集対象ファイル単位で書く。

- [ ] `src/path/to/file.py`  # 実装対象
- [ ] `tests/path/to/test_file.py`  # 実装対象に対応する単体テスト

ただし、ファイル編集では表現しづらい成果物作成・生成・移行、Bashコマンド実行などが必要な手順としてもし存在するならば、作業単位として記載してよい。

- ファイル編集以外のToDoは原則として目的単位でまとめる
- 具体実行コマンドを細かく書くのは、順序・失敗時の判断・成果物がステップごとに異なる場合だけにする
- lint / format / test のような検証目的だけのコマンドはToDoに含めない
